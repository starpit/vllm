# Ferrite Metal Execution Architecture Options

## Context

Phase 4.6 complete: All 18 critical path operations have ICB recording infrastructure. Now deciding how to wire Metal execution into the ferrite-forward dispatcher.

## Option A: General-Purpose ICB Executor (RECOMMENDED FOR PHASE 5)

### Architecture
```
DSL → Solver → Instruction<W>[] (compile-time, static data)
                     ↓
         Runtime: MetalExecutor walks instructions once at init
                     ↓
         Each instruction.record_to_icb() encodes to ICB
                     ↓
         Forward pass: execute_icb() (single GPU call)
```

### Implementation
```rust
// In ferrite-forward/src/instr.rs
impl<W> Instruction<W> {
    pub fn record_to_icb(&self, ctx: &mut RecordingContext) -> Result<(), String> {
        match self {
            Instruction::RmsNorm(out, inp, wt_slot, wt_fn) => {
                let weight = wt_fn(ctx.wm, ctx.layer_offset);
                rmsnorm::record_rmsnorm(ctx, inp_buf, out_buf, weight.buffer(), ...)
            }
            Instruction::Gemm(..) => gemm::record_gemm(ctx, ..),
            // ... 18 critical path ops
        }
    }
}

// In ferrite-forward/src/metal_executor.rs
pub struct MetalExecutor<W> {
    icb: RecordingContext,
    device: MetalDevice,
    weights: W,
}

impl<W: CanonicalParams> MetalExecutor<W> {
    pub fn new(instructions: &[Instruction<W>], weights: W) -> Self {
        let mut ctx = RecordingContext::new(device, instructions.len());
        for instr in instructions {
            instr.record_to_icb(&mut ctx)?;
        }
        Self { icb: ctx, device, weights }
    }
    
    pub fn forward(&self, fwd_ctx: &ForwardCtx) -> OwnedTensor {
        // Execute pre-recorded ICB
        self.icb.execute_on_encoder(encoder, 0..self.icb.command_count());
    }
}
```

### Pros
- **Matches CUDA architecture**: Single `Instruction<W>::eval()` interpreter, just ICB-based
- **Already 90% implemented**: Phase 4.6 has all `record_*()` methods
- **Smaller binary**: One executor, ~500 lines total
- **Easier debugging**: Single execution path, standard Rust match
- **Flexible**: Can switch backends (CUDA eval vs Metal ICB) at runtime
- **Maintainable**: New ops add one match arm, not N specialized executors

### Cons
- **Runtime dispatch overhead**: One match per instruction at init (amortized, not per-forward)
- **No compile-time specialization**: Model constants read from `W::HEAD_DIM` at runtime
- **Indirect calls**: `wt_fn(ctx.wm, layer)` function pointer indirection

### Binary Size Impact
- One `record_to_icb()` match: ~50 lines
- One `MetalExecutor` struct: ~100 lines
- **Total: ~150 lines per crate, shared across all variants**

## Option B: Per-Variant Specialized ICB Executors

### Architecture
```
DSL → Solver → Instruction<W>[] (compile-time)
                     ↓
         Macro generates specialized MetalExecutor<Llama3_2_3B>
                     ↓
         Hard-wired ICB recording (no match, inlined instructions)
                     ↓
         Forward pass: execute_icb() (single GPU call)
```

### Implementation
```rust
// Generated by #[forward] macro per variant
pub struct MetalExecutor_Llama3_2_3B {
    icb: RecordingContext,
    device: MetalDevice,
    weights: Llama3_2_3BWeights,
}

impl MetalExecutor_Llama3_2_3B {
    pub fn new(weights: Llama3_2_3BWeights) -> Self {
        let mut ctx = RecordingContext::new(device, 47); // Known instruction count
        
        // Instruction 0: RmsNorm (inlined, no match)
        rmsnorm::record_rmsnorm(&mut ctx, 
            /* input */ 0, 
            /* output */ 1,
            weights.layers[0].input_layernorm.weight.buffer(),
            /* M */ num_tokens,
            /* N */ 3072,  // Baked constant
            /* eps */ 1e-5, // Baked constant
            "fp16"
        )?;
        
        // Instruction 1: Gemm (inlined)
        gemm::record_gemm(&mut ctx,
            /* A */ 1,
            /* B */ weights.layers[0].self_attn.qkv_proj.weight.buffer(),
            /* C */ 2,
            /* M */ num_tokens,
            /* K */ 3072,  // Baked
            /* N */ 9216,  // Baked (3 * num_heads * head_dim)
            "fp16"
        )?;
        
        // ... 45 more instructions, all inlined
        
        Self { icb: ctx, device, weights }
    }
    
    pub fn forward(&self, fwd_ctx: &ForwardCtx) -> OwnedTensor {
        self.icb.execute_on_encoder(encoder, 0..47);
    }
}
```

### Pros
- **Zero runtime dispatch**: No match statement, direct function calls
- **Compile-time specialization**: All model constants baked as literals
  - `HEAD_DIM=128` → literal `128` in kernel args
  - `INTERMEDIATE_SIZE=11008` → literal `11008`
  - `ATTN_SCALE=0.08838834764` → literal `0.08838834764f32`
- **Potential for future optimization**:
  - Constant folding: `M * K * N` computed at compile time
  - Dead code elimination: Unused branches removed
  - Kernel fusion: Adjacent ops could merge (future work)
- **Cleaner generated code**: No generic `<W>`, just concrete types
- **Better inlining**: Compiler sees full call graph, can inline aggressively

### Cons
- **Binary bloat**: ~100 lines × 57 Llama variants = 5,700 lines
  - Mitigated: Most code is data (buffer indices, constants), not logic
  - Actual bloat: ~2-3KB per variant (instruction encoding overhead)
- **Harder debugging**: 57 specialized executors instead of 1 general one
- **Maintenance burden**: Macro must generate correct executor per variant
- **No runtime flexibility**: Can't switch CUDA ↔ Metal without recompile

### Binary Size Impact (Estimated)
- Per variant: ~100 lines of generated Rust
- 57 Llama variants: ~5,700 lines total
- Compiled size: ~2-3KB per variant (mostly data, not code)
- **Total bloat: ~150KB for all Llama variants**
- Comparison: Option A is ~150 lines total (shared)

### Future Optimization Potential
1. **Kernel Fusion**: Adjacent memory-bound ops could merge
   ```rust
   // Instead of:
   rmsnorm::record(...);  // Write to slot 1
   silu::record(...);     // Read slot 1, write slot 2
   
   // Could generate:
   rmsnorm_silu_fused::record(...);  // Write directly to slot 2
   ```

2. **Constant Propagation**: Dispatch sizes computed at compile time
   ```rust
   // Option A (runtime):
   let threadgroups = (num_tokens + 255) / 256;
   
   // Option B (compile-time for fixed M):
   let threadgroups = 4;  // For M=1024, computed at macro expansion
   ```

3. **Buffer Layout Optimization**: Tile table size known at compile time
   ```rust
   // Option A: Vec<Option<TileEntry>> (dynamic)
   // Option B: [TileEntry; 47] (stack-allocated, fixed size)
   ```

---

## Recommendation

**Start with Option A for Phase 5**, but preserve Option B as a future optimization path.

### Rationale
1. **Phase 5 goal**: Prove Metal execution works end-to-end
   - Option A gets us there faster (90% done)
   - Option B requires macro surgery (2-3 days extra work)

2. **Binary size is acceptable**: 150KB bloat is negligible
   - vLLM binary is already ~500MB (CUDA kernels, models)
   - 150KB = 0.03% increase

3. **Optimization is premature**: 
   - ICB execution is already fast (single GPU call)
   - Dispatch overhead is one-time at init, not per-forward
   - Real bottleneck is kernel performance, not dispatch

4. **Option B can be added later**:
   - Add `#[metal(specialized)]` attribute to opt-in per variant
   - Macro generates specialized executor only when requested
   - Fallback to Option A for non-annotated variants

### Migration Path (Post-Phase 5)
```rust
// Phase 5: General executor (default)
#[forward]
fn llama() { ... }

// Phase 6+: Opt-in specialization
#[forward]
#[metal(specialized)]  // Generate specialized ICB executor
fn llama() { ... }
```

## Decision Log

- Reason: Faster to implement, matches CUDA architecture
- Future: Revisit Option B after Phase 5 complete and benchmarked

3. Is kernel fusion worth the complexity?
   - MLX does generic elementwise fusion, not per-variant
