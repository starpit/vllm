# Vision DSL — Phase G handoff

**Branch:** `feat/rust`, worktree `.claude/worktrees/multimodal`.
**Goal:** lift the vision tower into a `#[vision_forward]` DSL body, mirroring how text decoders are described. Each MM arch ends up with two backbones — text (`#[forward]`) and vision (`#[vision_forward]`) — composed at runtime via the existing `MmEmbedSplice` op. Supersedes the MULTIMODAL_HANDOFF.md "Phase G — Gemma3-MM / SigLIP" framing, which assumed a non-DSL `ferrite-vision` shared module.

**Why now:** with 3+ VL/MM arches imminent (Qwen2-VL + Qwen2.5-VL + Gemma3-MM/SigLIP, internvl/llava/pixtral on the horizon), the imperative ~1k-line per-arch `vision.rs` (931 + 989 lines today) is the wrong cut. Hybrid DSL gives per-block fusion, const-prop, and reduces each new tower to ~30 lines of math. The first port is the expensive one; each subsequent arch is the payoff.

**G.6 — Port Qwen2.5-VL.** The 805-line imperative `crates/ferrite-model-qwen2-5-vl/src/vision.rs` is the next target. Qwen2.5-VL is materially harder than Qwen2-VL — the existing DSL doesn't express five things the encoder needs:

1. **Per-layer attention switching.** 28 of 32 blocks run windowed varlen-attn; layers in `fullatt_block_indexes = [7, 15, 23, 31]` run full image-frame attn. Three options for the body surface (handoff originally listed these — now have to pick one):
   - (a) Two `#[vision_forward]` bodies, one for window layers + one for full, with a wrapper that dispatches per layer index. Worst because the macro doesn't currently support partial-body invocations.
   - (b) One body with a runtime-conditioned varlen-attn op — `varlen_attention(q, k, v, cu_seqlens_full, max_seqlen_full)` vs `varlen_attention(q, k, v, cu_seqlens_window, max_seqlen_window)` calls in the SAME loop, plus a static `if layer in [...] { ... } else { ... }` selector that the macro unrolls at expand time. Cleanest.
   - (c) `fullatt_block_indexes` baked as a const lookup inside an `if` expression in the body. Same as (b) but with the indices baked into the macro instead of declared inline. Slightly less readable.
   Recommended: (b). Add `if layer in [literal_array] { stmts } else { stmts }` to the parser; classify expands to the appropriate branch per unrolled layer.

2. **Two cu_seqlens externs + max_seqlen pairs.** Today's DSL has one `cu_seqlens` + one `max_seqlen` extern (vision-prelude). Qwen2.5-VL needs `cu_seqlens_full` + `cu_seqlens_window` + `max_seqlen_full` + `max_seqlen_window`. Add to `classified::ExternKind` (vision variants), wire `extern_shape` arms (cu_seqlens are opaque rank-1, max_seqlens are scalar opaque), thread through `ForwardCtx` (one TensorView field per cu_seqlens, one usize per max_seqlen).

3. **`embedding_gather` op.** Tokens are gather-permuted into window order on entry (`x_perm = embedding_gather(x, window_index)`); cos/sin tables are also gather-permuted to match; output is unpermuted post-merger via a reverse-permutation gather (`out = embedding_gather(merged, reverse_indices)`). New `OpKind::EmbeddingGather`, `EmbeddingGatherImpl` + `Instruction::EmbeddingGather` variant + eval calling `kernels::embedding_gather`. New externs: `window_index` (rank-1 u32), `reverse_indices` (rank-1 u32). The `cos` / `sin` externs already exist; the body just calls `embedding_gather(cos, window_index)` to permute them inline.

4. **SwiGLU MLP.** `down(silu(gate(x)) · up(x))` with bias on all three. Expressible today as `gate = bias_add(gemm(x, gate_proj), gate_proj.bias); up = bias_add(gemm(x, up_proj), up_proj.bias); mlp = gemm(silu(gate) * up, down_proj); out = bias_add(mlp, down_proj.bias);`. The `*` op already exists; `silu` already exists. Add a `silu_and_mul_fused` op as a fusion target so the existing `kernels::silu_and_mul_fused` kernel runs (the FUF can match the `silu(gate) * up` pattern and emit one fused op). Probably defer the fusion to a follow-up; the unfused chain compiles today.

5. **K=3420 cuBLAS pad workaround.** `down_proj.weight` ships with K=3420 (= `vision_intermediate_size` on Qwen2.5-VL-3B), which cuBLAS bf16 GEMM rejects with `CUBLAS_STATUS_INTERNAL_ERROR`. Imperative `vision.rs` calls `pad_linear_k_to_mult8` at load time (zero-fills K to next multiple of 8) and concats-with-zero-pad on the activation side before the GEMM. Two cleanest plumbings:
   - Manifest hint: extend `weights.json` to declare `down_proj` as `{ "shape": [...], "k_pad_mult": 8 }` so the macro's loader pads at H2D time.
   - Macro arg: `#[vision_forward(k_pad_weights = ["mlp.down_proj"], ...)]` listing weights to pad. Less manifest-y but more explicit.
   The activation-side concat-with-pad happens inside the body — needs a new `pad_zero_columns` op or an attribute on the gemm call. Probably worth a small new op (`zero_pad_dim1(x, n)`) that matches a one-line kernel.

## Non-goals

- No TP for vision in v1. Replicated weights stay; no AllReduce/AllGather extension.
- No new pyo3 / vllm-cuda / cuda_worker surface. Touch budget on those crates: 0 lines.
- Existing imperative `vision.rs` files don't survive G.5/G.6 — they're rewritten, not paralleled. (Per the "no parallel impls" feedback.)
- `ferrite-vision` is host-glue ONLY. GPU compute lives in OpKinds. If a helper does `kernels::*` work it belongs as an OpKind, not a shared function.
- No attempt to merge text and vision into one body. They run at different times in the request lifecycle, with different KV semantics — keep them as peer compiled forwards.

## Open questions to resolve before G.3

1. **Workload bucketing key.** RESOLVED: bucket on **batched-total flat L** (the concatenated varlen length the kernel actually launches over), not per-image. Mirrors text-side `num_tokens` semantics — total across the batch, not per-sequence. Default sweep `workloads = [256, 1024, 4096, 16384]` covers single-image 224² (~256 patches), 448² (~1024), 672² (~2304), and ~4-image streamlit-class (~16384). The vision macro reuses the existing `workloads` attribute slot — no new key. Per-image `max_seqlen` is a kernel input, not a solver axis.
2. **Reshape DSL surface.** RESOLVED FOR G.3: deferred. `OpKind::Reshape` stays synthesized-only through G.3. The vision body has two explicit reshapes (`[L, H, D] → [L, H*D]` post-attention, `[L, embed] → [L/S², embed*S²]` pre-merger-MLP); the first is recoverable by per-head shape inference (same shape as text's QK-norm path), the second requires bound-arithmetic in the reshape target dims (`l_out = num_tokens / merge_factor`, `merge_hidden = embed_dim * merge_factor`). G.3's stub vision body avoids the merger reshape; the DSL surface for it lands in G.5 when we actually port qwen2-vl.
3. **Tuple-returning ops in the DSL.** RESOLVED: 2-target works. `vision_rope_arity_and_output_shape` test path validates `Stmt::AssignTuple` for 2-target via the `vision_rope` shape signature; 3-target is exercised by `MlaSplit`. No further code change needed.

## G.6.10 — Image-path coherent + e2e green

`ebfa490ba`. Two fixes turned the qwen2.5-vl image inference from "no image attached" to coherent captions:

1. **`W::INTERMEDIATE_SIZE` fallback to `vision_intermediate_size_padded`** (`codegen.rs::emit_canonical_params_impl`). Vision-only crates lack the `intermediate_size` bound, so the bake produced `INTERMEDIATE_SIZE = 0` — `silu_and_mul_fused`'s split-point ran at 0, the kernel emitted a `[L, 0]` empty activation, and the down gemm contracted to zero. 2. **Explicit `bias_add(down, mlp.down_proj.bias[layer])`** in the body. The unfused `Instruction::Gemm` calls `cublas.gemm(weight, ...)` and skips bias entirely; without the bias_add tile, `down_proj.bias` was silently dropped on every block. `FusedGemmBias` now claims the down gemm + its bias_add via the existing `(Gemm, BiasAdd)` matcher.
