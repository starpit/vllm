## Compositional norms (post-rebase reconciliation)

ff-interpreter retired the explicit `OpKind::LayerNorm` / `OpKind::LayerNormBias` DSL surface in favor of a compositional design: the DSL writes the math primitives (`mean(x); sub(x, m); rmsnorm(centered, w); bias_add(normed, w.bias)`) and an Impl matcher (`MeanSubRmsNormImpl` / `MeanSubRmsNormBiasAddImpl`) claims the trio/quad and lowers it to one fused kernel call. Per-arch LayerNorm minor-math variants live at the Impl level instead of proliferating OpKind variants.

This handoff's older G.5.f and G.6 entries describe an `OpKind::LayerNormBias` + `Instruction::LayerNormBias` + `LayerNormBiasImpl` + `load_layered_layer_norm_bias` chain that was the original design before the rebase onto ff-interpreter. The landed `209b81fc9` adapts to ff-interpreter's compositional model:

- **No `OpKind::LayerNorm` / `OpKind::LayerNormBias`.** Qwen2-VL writes its norms (norm1 / norm2 / merger.ln_q) as `(mean, sub, rmsnorm, bias_add)` in the DSL body. The bias-side weight ref (e.g. `norm1.bias[layer]`) is structural-only — the matcher's `required_weights` returns ONE `LayerNorm`-typed accessor sourced from the rmsnorm's weight ref, and `load_layered_layer_norm` (or its vision-prefix sibling `load_layered_layer_norm_vision`) pulls both `<prefix>.weight` and `<prefix>.bias` from disk.
- **No singleton `LayerNormBiasImpl` / `Instruction::LayerNormBias`.** Both retired in favor of `MeanSubRmsNormBiasAddImpl` → `Instruction::MeanSubRmsNormBiasAdd` → `kernels::layer_norm_bias`.
- **No `load_layered_layer_norm_bias` loader.** Replaced by `load_layered_layer_norm_vision` (vision-prefix variant of the existing `load_layered_layer_norm`); codegen routes by `Prelude::Vision`.
- **No `BackboneLayout::Vision` flag.** Vision falls into the existing `BackboneLayout::Encoder` arm naturally — vision terminals aren't `gemm(_, lm_head)`, so `backbone_layout()` reports `Encoder` for vision the same way it does for ModernBERT.
- **Kernel-class summary.** The norm path now reports as `mean_sub_rms_norm_bias_add` (HEAD's name), not `layer_norm_bias`.

Qwen2.5-VL is unaffected by this reconciliation — its vision blocks use plain RMSNorm (no mean subtraction, no bias) so the body's `rmsnorm(x, w)` already matches HEAD's `RmsNormRefImpl` with no decomposition needed.

**Why now:** with 3+ VL/MM arches imminent (Qwen2-VL + Qwen2.5-VL + Gemma3-MM/SigLIP, internvl/llava/pixtral on the horizon), the imperative ~1k-line per-arch `vision.rs` (931 + 989 lines today) is the wrong cut. Hybrid DSL gives per-block fusion, const-prop, and reduces each new tower to ~30 lines of math. The first port is the expensive one; each subsequent arch is the payoff.

Matches HF Gemma3-MM's `masked_scatter` ordering (`transformers/models/gemma3/modeling_gemma3.py:907-913`). Affects only Gemma3-MM (only arch with `embed * sqrt(hidden_size)` and a vision encoder); Qwen2-VL / Qwen2.5-VL / Llama / etc are byte-equivalent (no ScalarMul on the Embed → splice goes after Embed unchanged). Post-fix: R1 → "Here's a description of the image: Shape: The image is a circle. Color: The circle is a solid, vibrant red color." Tile-count delta: `gemma-3-4b-it 660/277 → 661/277` (+1 tile from FUF rewiring), `gemma-3-4b-it-mm 992/447` unchanged, all qwen2-vl / qwen2.5-vl / commandr baselines unchanged.

2. **~~Second-MM-request returns NaN logits / `<pad>` tokens.~~ FIXED in `Instruction::Reshape` + `Instruction::RopeAppend` eval (interpreter use-after-free).** Diagnosis (via per-instr `FERRITE_DEBUG_DUMP_PATH` whole-tile NaN scan that distinguishes Owned/Reshaped/View): R2's first sliding-attention prefill received Q/K/V with rows 128..271 entirely NaN (~50% of every per-head row), even though the per-instr dump claimed the producing slots had `bad=0`. The mismatch was the dump skipping `TileEntry::Reshaped`. Walking the `Reshaped`'s underlying memory directly showed it was being overwritten *during* sliding_attention — sliding_attention's output `alloc_tensor` was handing back the same physical block that `Instruction::Reshape` had freed earlier the same forward pass. **Root cause:** when the FUF compiler emits `Instruction::Reshape(in_slot, out_slot, ...)` with `out_slot == in_slot` (in-place slot reuse), the eval path overwrites `tiles[out_slot]` with a `TileEntry::Reshaped { ref_slot: in_slot, tensor }` — which drops the previous `TileEntry::Owned(OwnedTensor)`, freeing its block back to the caching allocator. The new `Reshaped` still holds the old GPU pointer. Subsequent `alloc_tensor` calls in the same forward (e.g., a downstream attention output) reused that freed memory; the kernel wrote there while still reading the Reshaped, producing torn writes (NaN / extreme magnitudes) at the soft-token rows specifically because the allocator pattern made the collision bite there in R2 but not R1. Same bug latently affected RopeAppend's three Q/K/V reshapes. **Fix:** added `pinned_owned: Vec<OwnedTensor>` to `InterpreterCtx`. Before any in-place Reshape overwrite (in `Instruction::Reshape::eval` and `Instruction::RopeAppend::eval`), `mem::take` the prior entry and stash any `Owned` into `pinned_owned` so the OwnedTensor lives until the end of the run, keeping the underlying GPU memory live for every Reshaped that aliases it. +43 lines, single file. **Why R1 worked, R2 failed, `reset_prefix_cache` "fixed" it:** allocator state. R1's downstream allocations didn't happen to land on top of R1's freed Q/K/V. R2's did, because the post-R1 allocator state shifted the collision into a load-bearing slot. `reset_prefix_cache` only mutates hash maps but it perturbs allocator usage enough downstream to dodge the collision. With the fix, the freed-but-aliased path no longer exists, so allocator state can't re-trigger it. Verified: R1 red coherent, R2 blue coherent on a fresh server, no flag tricks; gemma3-mm 4/4, qwen2-vl 8/8, qwen2.5-vl 8/8.

   **Architectural followup (not load-bearing for the fix).** The compiler-side contract on `Reshaped::ref_slot` ("pins the slot whose `OwnedTensor` actually owns the storage") only holds when `out_slot != in_slot`. The codegen drop-pass should either guarantee distinct slots when the input is Owned, or move ownership of the OwnedTensor to a side-table at codegen time. The runtime `pinned_owned` is a safety net that papers over the codegen gap; making `out_slot != in_slot` an invariant would let `pinned_owned` go away and surfaces real codegen bugs as compile errors instead of silent UAF.

1. ~~**Chunked-prefill across image-placeholder boundaries is broken (all MM arches).**~~ **RESOLVED.** Two coupled fixes in `cuda_worker.rs`, plus one new e2e regression test:

   **Material differences vs Python vLLM still open (TODOs, ordered by impact):**
   - **(a) No scheduler-side encoder budget / `disable_chunked_mm_input` knob.** Python's scheduler can roll back `num_new_tokens` to stop a chunk just before an image when the encoder cache budget would otherwise be exhausted, OR refuse to chunk MM input at all when configured (`vllm/v1/core/sched/scheduler.py:1161-1196`). Our scheduler always schedules whatever fits in `max_num_batched_tokens` and lets the model runner cache encoder output for the whole request. Risk: at high concurrency with many large-image requests, our `mm_embeds_cache` can grow to N_concurrent_reqs × per_req_image_bytes with no upstream backpressure — Python caps this via `encoder_cache_size`. Fix lives in `vllm-rs/crates/vllm-core/src/scheduler.rs` (or wherever the v1 scheduler lives) + a new `EncoderCacheManager`-equivalent shared between scheduler + worker.
   - **(b) Cache key is `req_id`, not `mm_hash`.** Python keys `encoder_cache` by per-image content hash so two requests carrying the same image share one encoder run. Ours runs the encoder per-request even when two concurrent requests carry byte-identical images. Pure efficiency leak — no correctness impact. Fix: thread per-image `mm_hash` from the API/engine layer into `MultimodalData` and switch `mm_embeds_cache` keying.
   - **(c) Cache freed only at `release_request`, not per-image after consumption.** Python frees `encoder_cache[mm_hash]` once `num_computed_tokens >= start_pos + num_encoder_tokens` for that image — the encoder output is then permanently in KV cache, not needed again. Ours holds it through every decode step until generation ends. For a long-running generation with images, holds ~1.5 MB/image past the point of usefulness. Fix: track per-image consumption progress in the worker and drop entries from `mm_embeds_cache` (or migrate to a per-image keying first per (b), then track mm_hash consumption).
   - **(d) Mixed-batch eager prefill path still skips MM splice (`cuda_worker.rs` line ~7910, "Mixed-batch eager prefill: MM splice not yet plumbed through this slow path").** A VL prefill that lands in the mixed decode-graph + prefill-eager split (rare — concurrent decode reqs at first-image-prefill step) still passes `mm_inputs: None`.
